One of nylon's key features is compatibility with standard WireGuard clients (iOS, Android, Windows, etc.). These are called **Passive Nodes/Clients**.

::::caution
Stock WireGuard clients interoperate with a nylon mesh **only** when it uses a vanilla-compatible obfuscation profile (the default). Without an `obf` section in `central.yaml`, nylon pins the handshake headers to `h1=1-1` through `h4=4-4` — the vanilla WireGuard message types — so the mesh speaks byte-compatible vanilla WireGuard. The same byte-compatibility can be pinned explicitly with `nylon-genesis --compat`. If your mesh enables a profile that deviates from these vanilla-pinned values, stock WireGuard clients cannot complete handshakes with nylon peers. See [Obfuscation](/guides/obfuscation) for how profiles work.
::::

## How it Works

Passive nodes do not participate in the routing protocol. Instead, they connect to a **Gateway Node** (a regular nylon node) which advertises their presence to the rest of the network.

```mermaid
graph LR
    subgraph "Nylon Mesh"
        N1[Node A]
        N2[Node B]
        N3[Node C]
        N1 <--> N2
        N2 <--> N3
        N3 <--> N1
    end
    subgraph "Passive Clients"
        P1[WireGuard iOS Client]
        P2[WireGuard Android Client]
        P3[WireGuard Windows Client]
    end
    P1 <--> N1
    P2 <--> N2
    P3 <--> N2
```

<Steps>

1. ### Configure the Passive Node

   Use any WireGuard app to generate a keypair. Note the public key.

2. ### Update Central Configuration

   Add the passive node to your `central.yaml`. Passive nodes should **not** have endpoints.

   ```yaml title="central.yaml"
   routers:
     - id: node-1
       pubkey: <GATEWAY_NODE_PUBLIC_KEY>
       addresses: [10.0.0.1]
       endpoints:
         - "node1.example.com:57175"
     # ... other routers ...

   clients:
     - id: my-phone
       pubkey: <PHONE_PUBLIC_KEY>
       addresses:
         - 10.0.0.5

   graph:
     - node-1, my-phone # Connect the passive node to a gateway node
   ```

3. ### Connect to a Gateway

   In your WireGuard app, set the `Endpoint` to the address of a router that is graph-adjacent to this client (an edge such as `node-1, my-phone` in `central.yaml`). A router with no graph edge to the client never creates its WireGuard peer and drops its handshakes.

   ```ini title="wireguard.conf"
   [Interface]
   PrivateKey = <PHONE_PRIVATE_KEY>
   Address = 10.0.0.5/32

   [Peer]
   PublicKey = <GATEWAY_NODE_PUBLIC_KEY>
   Endpoint = gateway.example.com:57175
   AllowedIPs = 10.0.0.0/24 # or whatever you want to route through nylon
   ```

</Steps>

## Limitations

- A single WireGuard peer entry in a client app has one active `Endpoint` at a time — this is standard client-side WireGuard behaviour, not a mesh constraint. The mesh itself accepts a passive client adjacent to multiple gateways; to reach several of them, configure multiple profiles sharing the same private key (see [Dynamic Routing](#dynamic-routing)).
- They cannot forward traffic for other nodes.
- They rely on the gateway node for connectivity to the rest of the network.

## Dynamic Routing

Even though passive nodes do not participate in routing, they can still benefit from nylon's dynamic routing capabilities. By configuring multiple VPN profiles using the same private key, a client can switch between gateways automatically.

::::tip
Depending on the WireGuard app, there may be features like Scene-based routing in [Shadowrocket](https://en.wikipedia.org/wiki/Shadowrocket) that can automatically switch the gateway node/VPN profile based on network conditions.

This can help your passive node maintain optimal connectivity, even when you travel.
::::

### No Keepalive Needed

::::note

You do not need to enable Persistent Keepalive, or any heartbeat mechanism for this simple use case.

::::

When a gateway is the **sole advertiser** of a passive client's prefix, nylon retains the route for that client indefinitely, ensuring it remains reachable even if it goes idle for an extended period. The indefinite hold starts from the last live advertisement: a configured client that has not sent a packet since the gateway (re)started is not advertised until it does — any authenticated packet, including a keepalive, bootstraps it. The hold is skipped while another gateway's advertisement or route for the prefix is visible (a route with a finite metric from a different source); graph adjacency alone does not suppress it — the competing advertisement, refreshed by the gateway that now holds the client, is what ends the hold. Refreshes continue while the client keeps talking (silence under `ClientDeadThreshold`, 6 s); the last refresh sets the 3-second advertisement TTL, and the 1-second garbage collection removes the lapsed advertisement — so the prefix is withdrawn roughly 8-10 seconds after the client's last packet. With multiple gateways, enable Persistent Keepalive to keep the route alive during idle periods, with an interval faster than `ClientDeadThreshold` (6 s default) — 5 s as used by the passive-roaming e2e test, since the commonly recommended 25-second Persistent Keepalive is too slow and the route lapses; the conservative bound is under `ClientKeepaliveInterval` (3 s). With a sole-advertising gateway, you should only enable Keepalive if:

1. You need other nodes to be able to initiate connections to the client after long periods of silence.
2. You really wish to drain the battery of the client device for some reason...

For mobile devices, leaving Keepalive disabled is recommended to maximize battery life.

> For a deep dive into how nylon handles roaming and keeps idle clients reachable, see the [Passive Nodes Reference](/reference/passive-nodes).
